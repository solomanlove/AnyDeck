# AnyDeck 华为分享改版方案（实施中）

最新分阶段进度与验收见 [harmony-share-delivery.md](harmony-share-delivery.md)：UI 第一批已落地，大文件完成至 1 GiB 的离线验证，手机与完整发布验收仍待完成。以下保留早期改版依据与范围。

## 2026-10-28 实施记录

- 已新增位于「投屏接收」下方的独立「鸿蒙互联」侧边栏和页面，移除旧手填 IP/端口测试卡片。页面不依赖设备管理中的已连接手机。
- 主窗口启动唯一接收服务，自动计算当前网卡广播地址；私有核心在接收窗口中同时广播、发现和等待任意来机，收到单文件 offer 后等待用户确认，30 秒未确认则拒绝。页面切换不停止服务。
- 已实现点击设备选文件、拖拽单文件、发送确认、取消、接收弹窗和最近路径记录。核心仍将发送/接收能力标为实验状态，仅支持同一 Wi-Fi 下单个 1 MiB 内普通文件；B/C 阶段的多文件、大文件、进度、系统通知、完整记录和发布验收尚未完成。
- 协议源代码和 arm64 原始制品只在私有仓库；主仓只保存 UI、IPC、锁定 commit 与 SHA-256，构建时将已锁定二进制装入 App。静态、单元及包内签名校验已完成。
- 真机阶段：Mac `192.168.1.3` 与 nova 12 Ultra `192.168.1.146` 同网段，新 App 自动发现手机。手机开启“所有人可见”后，用户确认电脑→手机成功；随后手机→电脑成功，App 显示新接收目录中的文件。用户实际选择的文件并非预备的测试 txt，本轮没有读取内容或核对端到端哈希。之后修复了自广播被列为附近设备的问题；该修复已进入最终制品，但尚未对最终制品再次真机复验。

## 1. 对照依据与边界

- 本机安装的鸿蒙星河互联 1.0.8（66.3000）：现场观察到单窗口发现页、顶部本机身份、中部持续搜索、底部“找不到设备”引导；安装包中文文案确认拖拽文件到设备头像、点设备再选文件、手机端选择本机、接收确认、发送/接收记录、失败重试和设置权限等入口。未在本轮观察到手机在线时的完整页面和传输弹窗，因此其细节以下列流程和文案为依据，不把原型当作像素复刻。
- AnyDeck 现状：收发藏在“投屏接收”的测试卡片中，手填本机/广播/手机 IP 和端口；每次操作才启动原生进程。私有核心 IPC `hello` 仍声明 `send=false, receive=false`，当前仅有 120 秒、单个普通文件、1 MiB 的实验命令。之前 nova 12 Ultra 的 39 B 文件双向传输通过；新构建 App 内的完整交互还未真机验收。
- 产品目标：在左侧“投屏接收”条目下方新增一级侧边栏“鸿蒙互联”，点击后进入独立页面；原“投屏接收”页继续管理 AirPlay/DLNA；完成“发现附近手机 → 选中/拖入文件 → 确认发送”和“手机发起 → Mac 弹出确认 → 保存/打开”。发现与接收不依赖设备管理中的已连接手机或 HDC/ADB 连接，普通用户看不到网络参数。

## 2. 页面与交互

| 页面/状态 | 用户可见内容 | 操作与反馈 |
| --- | --- | --- |
| 鸿蒙互联·发现页 | 左侧位于“投屏接收”下方的独立一级入口；本机身份、独立服务状态、附近设备、拖拽区域、权限/网络状态 | 进入页面自动发现；接收监听由主窗口服务托管，离开页面仍可响应手机来件。无设备时保留接收状态与“找不到设备？”引导。 |
| 设备已发现 | 手机头像、名称、可用状态、最近传输 | 点击头像选文件；拖文件到头像立即进入发送确认。 |
| 发送确认/队列 | 文件名、大小、目标手机、传输进度 | 发出前确认；进行中可取消；完成显示“手机已确认接收”或准确失败原因。 |
| 收到请求 | 系统通知加 App 内弹窗：来源、文件清单、大小 | 默认需人工“接收/拒绝”；超时自动拒绝；接收后显示保存位置与“在 Finder 中显示”。 |
| 互传记录 | 我发送的/我接收的、搜索、状态、时间 | 打开文件/所在目录；失败任务可重试；删除记录和删除文件分开确认。 |
| 页面设置与诊断 | 本机显示名称、接收保存目录、通知、设备可见性、权限状态 | 从鸿蒙互联页右上角进入；网络接口自动选取，仅诊断区展示脱敏 IP/端口，普通流程无输入框。 |

### 核心流程

1. **发现**：主窗口启动单个 Share Core 服务，独立于设备管理/HDC/ADB 的已连接设备列表；自动读取活跃 Wi-Fi 接口、IPv4 与真实子网掩码计算广播地址；合并 BLE 与 CoAP 结果，按设备稳定标识去重，断线/网络切换时刷新。手机不在附近时，页面仍显示“等待接收”和排障入口。
2. **发送**：点手机选文件、把 Finder 文件拖到设备头像、macOS“共享到 AnyDeck”三种入口汇入同一待发送队列。先校验数量/大小/类型，再显示确认；进度、取消、结果由核心事件驱动。
3. **接收**：由独立服务在 App 运行期间保持可发现并监听，不要求先扫描、选中或连接一台手机。收到 offer 后先解析来源、文件元数据和大小限制，再推送系统通知和 App 内确认；用户接受后才写入临时目录，校验并原子移入保存目录；拒绝/超时/取消均清理会话。
4. **记录**：每个任务保存方向、设备、文件摘要、状态、时间、保存路径；最近任务在鸿蒙互联页底部展示，完整列表由页面“互传记录”打开。重启 App 后保留记录，但不自动重发。

## 3. 结构与改动范围

| 层 | 计划改动 |
| --- | --- |
| 路由/UI | 新增左侧一级侧边栏“鸿蒙互联”和独立 Dashboard route，位置紧接“投屏接收”；从 `ReceiverDashboardTab` 移除临时测试卡片，在新页面拆分设备区、DropTarget、任务面板、接收弹窗、记录面板和设置面板。UI/Controller/Model 分文件，单文件小于 500 行，zh/en 文案及明暗主题同步。 |
| 主仓 IPC | `ShareCoreClient` 只暴露稳定的发现、任务、取消、接收决策事件；主窗口唯一服务实例负责生命周期，不能绑定鸿蒙互联页面的 Widget `dispose`；其他窗口通过现有广播/Provider 订阅。主仓不包含协议字段或原生源码。 |
| 私有核心 | 把实验的一次性 CLI 改为长驻、有界事件流：`startDiscovery`、`sendFiles`、`incomingOffer`、`accept/reject`、`progress`、`cancel`、`networkChanged`。保留超时、大小、路径与并发上限；通过版本化 IPC 升级能力声明。 |
| macOS | 自动网络接口/子网信息，Finder 拖拽及共享扩展，系统通知与权限引导，保存目录书签；仅在用户实际使用时申请相关权限。 |
| 交付 | 私有制品按固定 commit、SHA-256 和签名安装；主仓只更新锁文件、UI、IPC 和测试。 |

## 5. 验收清单

- 首次启动/权限拒绝/手机离线/多网卡/VPN/热点/不同子网，界面可解释当前状态且无需手填 IP。
- Finder 拖入、点设备选文件、手机向 Mac 发起，各走完整确认、进度、取消、成功/失败链路。
- 拒绝与超时不落盘；同名文件不覆盖；接收目录可打开；失败原因可追踪且日志不记录文件内容与密钥。
- 离开鸿蒙互联页后，App 仍能收到手机发起的来件并弹出确认；关闭接收服务或退出 App 时回收 Share Core、BLE 广播和监听端口；原投屏接收页 AirPlay/DLNA、HDC 文件页回归通过。
